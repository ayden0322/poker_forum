# Codex(GPT-6 Astra)競猜頁三點視覺方案討論(2026-09-13,續接審查 session)

## A. 三點各自的方案比較與推薦

**推薦組合：44px 高的緊湊賠率按鈕＋真實隊徽與英文隊名＋預設「全部聯盟、依台灣時間排序」。**先讓使用者直接看見有哪些比賽，再用聯盟篩選縮小範圍。

以下是設計與實作提案；資料來源、現有 API 與 parser 狀況沿用你提供的已查證前提。

### 1.「賠率的欄位不用這麼大」

| 方案 | 具體呈現 | 優點 | 代價與風險 |
|---|---|---|---|
| **① 緊湊雙組按鈕，推薦** | 標籤與賠率橫排，例如「主勝 1.37」；每格高 44px。桌機勝負、大小分同列；手機分兩列。 | 五個選項全部可見；降低面積但保留可點性。 | 需拆分市場分組；桌機主欄太窄時也必須換列。 |
| ② 列表只顯示勝負，大小分展開 | 第一列三格；「大小分」點開後顯示兩格。 | 初始卡片最矮。 | 大小分可發現性下降，多一次點擊；容易被理解為選項不足。 |
| ③ 卡片只留「選擇競猜」入口 | 列表專注隊伍與時間，點入面板才看賠率。 | 賽事資訊最突出，清單密度最高。 | 比較不同賽事需反覆開關面板，不適合這次需求。 |

**推薦①。**縮掉的是按鈕內的空間與直向排版，不是操作面積。未選中的賠率改中性深灰；青綠只保留選中態與連結。

具體規格：

- `OddsButton`：`h-11 min-h-11 px-2 inline-flex items-center justify-center gap-2 rounded-md border`
- 標籤：`text-xs text-gray-600`
- 賠率：`text-sm font-semibold font-mono-stadium tabular-nums text-gray-900`
- 桌機操作區：`grid grid-cols-[3fr_2fr] gap-3`
- 手機操作區：上下兩組，各自 `grid-cols-3`／`grid-cols-2`

操作区桌機約 64px 高，手機約 136px 高，均含組名。這是提案尺寸，尚未經實機排版驗證。

### 2.「要有隊伍 logo」

| 方案 | 具體呈現 | 優點 | 代價與風險 |
|---|---|---|---|
| **① 正規化保存球隊 ID，API 回傳 logo URL，推薦** | schema 增加主客隊 nullable ID；parser 取值；markets API 回傳圖片 URL。 | 使用既有來源，識別穩定；可持續涵蓋新賽事。 | 舊資料需回填；必須按運動類型組 URL，不能只用 ID。 |
| ② 前端手工英文隊名→logo 對照表 | 延伸 `team-meta.ts`，加入足球隊徽映射。 | 不依賴 migration，可先展示部分隊伍。 | 約 140 隊維護負擔高；別名、升降級容易漏，不適合作為正式主路徑。 |
| ③ 在①上增加自有圖片代理／快取 | 圖片經站內服務快取再顯示。 | 可控制圖片尺寸、失效與外部依賴。 | 增加儲存、快取與營運工作；目前使用量不值得優先投入。 |

**推薦①，暫不加圖片代理。**短期接受「logo＋英文名」，不要等中文隊名齊全才上線。

顯示規格：

- 隊徽：`size-7 sm:size-8 shrink-0 object-contain`，不加裝飾圓底。
- 隊名：`text-sm sm:text-base font-semibold leading-5`，手機允許換行。
- 無 ID 或圖片載入失敗：同尺寸中性縮寫徽章，避免版面跳動。
- `TeamLabel` 新增可選 `logoUrl`；相鄰已有隊名時圖片 `alt=""`。
- 舊呼叫端未傳 URL 時保留既有映射能力。

**風險：**外部圖片可用性、使用條款與快取條件需要確認；這不代表需要新資料來源。若不同運動的球隊 ID 可能重複，識別與 URL 組合必須使用「運動類型＋ID」。

### 3.「十個聯盟要逐一點才知道有哪些比賽」

| 方案 | 具體呈現 | 優點 | 代價與風險 |
|---|---|---|---|
| **① 全部聯盟時間表＋聯盟篩選，推薦** | 預設列出當日所有聯盟賽事；日期分組、組內依時間排列；需要時才篩選聯盟。 | 不點分頁就能知道有哪些比賽，符合台灣使用時段。 | 需要彙總資料與完整載入狀態；不同運動的盤口名稱要清楚。 |
| ② 按日期，再按聯盟分區 | 同一頁顯示德甲、英超、MLB 等分組，各區依時間排。 | 聯盟歸屬很清楚，適合只看固定聯盟者。 | 同時段賽事被拆散；仍需跨多個區塊掃描。 |
| ③ 聯盟概覽卡 | 每聯盟顯示「今日 6 場／下一場 21:30」，點入看完整賽程。 | 比只有聯盟名稱更有資訊。 | 仍需逐個進入才能看對戰；增加一層導覽，未直接解決問題。 |

**推薦①。排序採「台灣日期 → 開賽時間」，聯盟只作為每張卡的標籤。**同時開賽再以聯盟、賽事 ID 固定排序，避免刷新後順序跳動。

頂部改為：

- 第一列：日期選擇，預設「今天」。
- 第二列：「全部聯盟」與「篩選聯盟」。
- 篩選面板內顯示十個聯盟與當日賽事數；這是賽程資料，不是參與人數或熱度。

#### 彙總 API 的選擇

| 路徑 | 優點 | 代價與風險 |
|---|---|---|
| 前端並行打 10 次 | 可作短期過渡，不必先加彙總端點。 | 冷快取可能帶來十次後端工作；局部失敗、排序及全域分頁都交給前端處理。 |
| **後端新增 `/predictions/markets`，推薦** | 統一時間篩選、排序、分頁與資料完整性；前端一次取得所需結果。 | 需要 API 契約與快取設計；不能只把十份全量資料包成更大的回應。 |

建議彙總端點回傳 `matches`、`nextCursor`、各聯盟當日賽事數，以及 `unavailableBoards`。重用現有板塊快取／查詢邏輯，不在每個頁面請求內重新抓外部賽事來源。

單一彙總請求**不會自動降低後端計算量**；收益來自共用快取與集中處理排序、分頁。前端十次並行僅保留為工期受限時的過渡方案。

## D. 導覽方案要處理的邊界情況

### 今天沒比賽的聯盟

- 預設「全部聯盟」只列有賽事的卡片，不渲染十個空分區。
- 篩選面板保留全部十個聯盟；零場顯示「今日無賽事」，仍可選取。
- 選到零場聯盟後，顯示「此聯盟在所選日期沒有可競猜賽事」，提供「查看其他日期」。
- 若某聯盟資料載入失敗，顯示「暫時無法取得」，**不能當成零場**。
- 「下一場在某日」只有取得真實下一場資料時才顯示，不能推測賽程。

### 跨日與台灣凌晨賽事

**一律以 `Asia/Taipei` 的實際日曆日期分組。**

例如歐洲當地週日晚間、台灣週一 02:30 的比賽，放在台灣週一，不歸回「週日夜場」。日期標題明示「台灣時間」。

彙總端點以台灣日期換算 UTC 查詢區間，採：

```text
開始時間 >= 所選日期 00:00（台灣）
開始時間 <  下一日期 00:00（台灣）
```

今天無可競猜賽事時，提供「查看明天」；不把明天的場次偷偷塞在「今天」下面。若未來提供「未來 24 小時」視圖，也應保留跨日分組標題。

### 一頁最多幾場

建議**每批 30 場、單次瀏覽最多保留 90 張完整卡片**，作為第一版可調整的產品參數：

- 初次 30 場。
- 點「載入更多賽事」再取 30 場；按鈕 `min-h-11 w-full`。
- 到 90 場後用下一頁替換列表，避免無限制增長。
- 返回前頁或賽事列表時，保留日期、聯盟篩選與捲動位置。
- 不做自動無限捲動，讓使用者能抵達頁尾玩法。

分頁用全域排序游標，而不是各聯盟各取幾場再拼接，否則可能漏掉真正較早開賽的比賽。游標應含排序位置與查詢條件；以 `matchId` 去重。

### 快取刷新與封盤

彙總快取可沿用 30 秒更新節奏，但分頁需考慮這段期間賽事封盤、移除或改時：

- 列表刷新不強制把使用者捲回頂部。
- 新增／改時可能改變排序，提供重新整理入口。
- 已封盤項目若尚留在畫面，停用選項並顯示狀態。
- 最終能否競猜仍由確認 API 判斷，不能把列表快取當成受理保證。

若要讓多批結果嚴格一致，需增加查詢快照或版本機制；這是額外工程，不包含在單純「新增彙總端點」之內。

## E. 實作順序與各步驟預估工時

以下以一位熟悉專案的工程師估算；假設可沿用現有資料存取、Redis 與 Docker 測試環境，不包含中文隊名整理及新討論系統。

| 順序 | 工作 | 預估工時 |
|---|---|---:|
| 1 | 定稿卡片尺寸、日期篩選及 API 欄位契約 | 2–3 小時 |
| 2 | 緊湊 `OddsButton`、`MarketGroup`、手機隊伍排列及選中狀態 | 4–6 小時 |
| 3 | nullable 球隊 ID migration、足球／棒球 parser、資料寫入與 markets URL 回傳 | 5–8 小時 |
| 4 | `TeamLabel` 圖片優先序、載入失敗 fallback、既有賽事回填方案 | 3–5 小時 |
| 5 | 彙總端點：台灣日期、聯盟篩選、排序、游標、快取與局部失敗 | 8–12 小時 |
| 6 | 日期導覽、全部聯盟、篩選面板、30 場載入與狀態保留 | 6–9 小時 |
| 7 | Docker 內 API／前端驗證、真正 Next.js build、360／390／768／桌機操作測試 | 5–8 小時 |

**合計約 33–51 小時，約 5–7 個工作天。**賠率縮小可先交付；隊徽與「全部聯盟」完成後再一起驗收完整體驗。

### Migration 風險評估

**屬加欄位的相容性變更，資料破壞風險較低，但鎖表與執行時間仍取決於資料庫引擎、版本及表大小。**這些條件目前未提供，不能承諾零停機。

建議發布順序：
